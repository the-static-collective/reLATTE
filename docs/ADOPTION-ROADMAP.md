# reLATTE Adoption Roadmap

**Status:** living relation map / open-world adoption plan  
**Inventory cut:** 2026-09-29  
**Current repository count in this cut:** 87, including reLATTE itself

This document records every Static Collective repository visible in the current archaeology pass and the relation reLATTE can presently justify.

It is deliberately **not** a final taxonomy.

The map must remain able to discover relations that are not visible yet.

## Open-world laws

```text
CURRENT MAP != COMPLETE RELATION GRAPH
OBSERVED EDGE != EXCLUSIVE ROLE
NO EDGE YET != NO RELATION
ADOPTION != OWNERSHIP
DONOR != DEPENDENCY
ANCESTOR != CURRENT AUTHORITY
COMPATIBILITY != AUTHORITY
PRIVATE != PUBLIC CONTRACT
RESEMBLANCE != ANCESTRY
A FUTURE EDGE MAY BE REAL EVEN IF THIS MAP CANNOT SEE IT YET
```

A repository may occupy several roles at once.

A later experiment may add, split, weaken, replace, or remove an edge without rewriting the fact that this earlier map existed.

## Relation statuses

- **OBSERVED** — current repository text, code, tests, or witnessed cross-repo work supports the relation.
- **CANDIDATE** — current synthesis suggests a useful reLATTE relation, but the cross-repo contract has not yet been proven.
- **ANCESTOR** — historically important donor/fossil; useful for lineage and rediscovery, but not current authority.
- **APPLICATION** — a domain that may consume or pressure-test reLATTE without defining the substrate.
- **UNRESOLVED** — repository was found, but this pass has not earned a stronger relation claim.

None of these statuses are permanent.

## Adoption motion

A relation should move through this road only when useful:

```text
DISCOVER
  ↓
DESCRIBE CURRENT EDGE
  ↓
NAME OWNER + NON-AUTHORITY
  ↓
EXTRACT SMALLEST PORTABLE CONTRACT
  ↓
BUILD SYNTHETIC FIXTURE
  ↓
RUN HOSTILE / NULL CONTROLS
  ↓
CROSS INTO A SECOND MATERIAL DOMAIN
  ↓
OPTIONALLY ADOPT
```

A repo does not need to be adopted merely because it is related.

reLATTE should prefer adapters, manifests, fixtures, and typed crossings over copying whole systems.

# Adoption priorities

The first adoption wave should be driven by the minimum end-to-end proof, not by repository popularity.

## Wave 1 — crossing substrate

Extract or conform to:

1. Project0 canonical bytes / identity.
2. Formation Trace real signatures.
3. TranchNode addressed payload references.
4. Band Runtime receive/hold/refuse semantics.
5. Trust perspective/moment boundary.
6. Autodisco transport as one replaceable carrier.

Target proof:

```text
A signs one crossing
→ B verifies
→ B receives
→ B holds
→ B admits or refuses
→ B signs receipt
→ restart
→ both histories reconstruct
```

## Wave 2 — divergence

Add:

- a second receiver with a different lawful disposition;
- Trust-style divergent accounts;
- GOATnote / jublEchat residual and return behavior.

Target proof:

```text
SAME CROSSING
→ B ADMIT
→ C REFUSE

both remain valid
neither becomes global state
```

## Wave 3 — environment and development

Add:

- Groove/Band weather;
- Haunted Toaster/Phonography susceptibility;
- MEMENTO uptake/reproduction;
- Iron Lung repair;
- BananaSpork mortality/successor.

Target proof: history changes future possibility without silently transferring authority.

## Wave 4 — composition

Add:

- National Treasure;
- BODY;
- SEAMforge;
- Founder Node;
- Convergent Codec;
- FogGlass.

Target proof: the ecology can discover a missing relation, distinguish real reuse from analogy, and route the change back to the correct owner.

## Wave 5 — ordinary life

Pressure-test with:

- Circle / BananaGram / Gramfork;
- Nourish Kids / 100pies;
- Static Live;
- cUps;
- Revival;
- other application repos.

The substrate only earns generality if materially different domains cross it without domain-specific hacks.

# How new relations enter the map

A future relation may be added even if neither repo currently mentions the other.

Minimum relation proposal:

```text
source_repo
target_repo
relation_type
current_evidence
what_is_preserved
what_changes
authority_owner
non_authorities
counterexample / failure condition
status
```

Recommended status progression:

```text
UNSEEN
→ CANDIDATE
→ OBSERVED
→ TESTED
→ ADOPTED
```

The reverse direction must remain possible:

```text
ADOPTED
→ PRESSURED
→ SPLIT / REVISED / RETIRED
```

No relation is immortal merely because it once worked.

## Closing law

> **The roadmap is a record of relations we can currently see, not a fence around relations the ecosystem is allowed to grow.**

Or more compactly:

> **MAP THE BODY. DO NOT TELL THE BODY IT MAY ONLY GROW WHERE THE MAP ALREADY HAS INK.**
